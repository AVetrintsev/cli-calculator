# Даты, время и календарная арифметика

Дата проверки: 2026-09-11. Исследователь: calendar_facts. Повод: пользователь добавил динамические значения «сегодня», «вчера» и пример `2026-10-09 + 4w3d`.

**Это исследовательские факты и условные примеры, а не выбор синтаксиса, библиотеки или поведения калькулятора.** Имена типов Temporal ниже служат проверенной терминологией. Их наличие в источнике не означает, что проект выбирает JavaScript или Temporal. Новые календарные политики пользователь ещё не согласовал.

## Какие значения различаются

| Понятие | Что известно | Что не следует предполагать |
|---|---|---|
| Дата (`PlainDate`) | Год, месяц, день в календаре | Время суток и часовая зона не заданы |
| Время суток (`PlainTime`) | Например, 14:30 | Дата, зона и конкретный момент не заданы |
| Дата со временем (`PlainDateTime`) | Например, 2026-10-09 14:30 | Без зоны/смещения это ещё не точный момент |
| Точный момент (`Instant`) | Положение на временной шкале | Локальные год, день и час требуют зоны |
| Дата со временем в зоне (`ZonedDateTime`) | Точный момент, правила зоны и календарь | Числовое смещение само по себе не заменяет правила зоны |

Это разделение явно описывает [документация TC39 Temporal](https://tc39.es/proposal-temporal/docs/). Следствие для «сегодня»: чтобы получить дату из текущего точного момента, нужна зона. Сама получившаяся дата может оставаться значением без зоны. Выбор системной, заданной пользователем или другой зоны — продуктовая политика, не свойство слова «сегодня».

Зона задаёт правила соответствия локального времени и UTC; `+03:00` задаёт только смещение. Зона с географическим именем может менять смещение для разных дат. RFC 9557 расширяет временные метки информацией в суффиксах, включая имя зоны; несогласованность указанного смещения и зоны требует отдельной обработки. Он также уточняет смысл `Z` относительно локального смещения. Нельзя считать `Z` указанием местоположения пользователя. [RFC 9557, §1, §2, §3.4](https://www.rfc-editor.org/rfc/rfc9557.html).

## Календарный день и фиксированные 24 часа

При смене смещения следующий календарный день с тем же временем на часах может наступить через 23 или 25 часов. Прибавление фиксированных 24 часов сохраняет прошедшую длительность, но может изменить показание часов. Temporal явно различает календарные компоненты и компоненты часов при арифметике в зоне. [TC39, ZonedDateTime.add](https://tc39.es/proposal-temporal/docs/zoneddatetime.html#zoneddatetimeaddduration-object-options-object--temporalzoneddatetime).

Локальная проверка для `America/Los_Angeles`:

| Начало | Следующий день, то же время | Прошло | Результат через фиксированные 24h |
|---|---|---|---|
| 2020-03-07 12:00 −08:00 | 2020-03-08 12:00 −07:00 | 23h | 2020-03-08 13:00 −07:00 |
| 2020-10-31 12:00 −07:00 | 2020-11-01 12:00 −08:00 | 25h | 2020-11-01 11:00 −08:00 |

Это вычисленные контрольные примеры, не прогноз будущих переходов. Указанные даты переходов согласуются с примерами [TC39 о часовых зонах](https://tc39.es/proposal-temporal/docs/timezone.html#examples-dst-disambiguation) и осенним примером [Python zoneinfo](https://docs.python.org/3/library/zoneinfo.html#using-zoneinfo). Метод проверки и версия данных приведены ниже.

В уже принятом языке калькулятора `d = 24h`, `w = 7d`. **Вывод для согласования:** календарный смысл `d` нельзя незаметно подставить вместо принятой фиксированной длительности, особенно после сохранения значения в переменной. Нужен явный выбор модели: сохранение различимых календарных компонентов, отдельная запись календарного периода или другое правило. Исследование этот выбор не делает.

Для чистых дат пользовательский пример не затрагивает переход часов: `4 × 7 + 3 = 31` день; `2026-10-09 + 31` календарный день даёт **`2026-11-09`**. Проверено средствами `datetime.date` и `timedelta`; арифметика этих типов документирована в [Python datetime](https://docs.python.org/3/library/datetime.html#date-objects). Это проверка календарного результата при указанной интерпретации, а не уже реализованный разбор `4w3d`.

## Месяцы, годы и конец месяца

В григорианском календаре високосный год делится на 4, кроме годов, делящихся на 100, которые должны делиться и на 400. Поэтому в феврале 2024 года 29 дней, в феврале 2025 и 2026 — 28. [US Naval Observatory, Leap Years](https://aa.usno.navy.mil/faq/leap_years).

Месяц не равен постоянному числу дней. Перевод календарных месяцев/лет в длительность требует даты отсчёта; при переводе дней в часы может понадобиться зона. Это видно в модели `Duration` и параметре `relativeTo`. [TC39, Duration.total](https://tc39.es/proposal-temporal/docs/duration.html#durationtotaltotalof-string--object--number).

При прибавлении месяца к 31 января целевой февраль не имеет 31-го числа. Temporal предоставляет как ограничение последним существующим днём (`constrain`), так и отказ (`reject`). Это две политики API, а не обязательное для нашего продукта правило. [TC39, PlainDate.add](https://tc39.es/proposal-temporal/docs/plaindate.html#dateaddduration-temporalduration--object--string-options-object--temporalplaindate).

Условные результаты **только если выбрать ограничение последним днём**; проверены локальной формулой:

- 2026-01-31 + один месяц → 2026-02-28.
- 2024-01-31 + один месяц → 2024-02-29.
- 2024-02-29 + один год → 2025-02-28.
- 2026-01-31 + сразу два месяца → 2026-03-31, но два последовательных прибавления по одному месяцу → 2026-03-28.

Последний пример — следствие выбранного ограничения, показывающее значение группировки операций. При отказе промежуточный несуществующий день был бы ошибкой. При модели «сохранять конец месяца» результат снова мог бы отличаться. Эти варианты не одобрены пользователем. Также календарный месяц не следует автоматически отождествлять с принятым количеством расчётных периодов в финансовых функциях.

## Пропущенное и повторённое местное время

Локальное время в зоне может соответствовать нулю или двум точным моментам. Весенний пропуск называется gap; осеннее повторение — fold. TC39 документирует стратегии выбора более раннего/позднего момента и отказа; такие стратегии не возникают автоматически из календарной записи. [TC39, Time Zones and Resolving Ambiguity](https://tc39.es/proposal-temporal/docs/timezone.html#ambiguity-due-to-dst-or-other-time-zone-offset-changes).

Проверенные случаи для `America/Los_Angeles`:

- `2020-03-08 02:30` не существовало. Попытки назначить смещение до/после перехода и вернуться из UTC дают соответственно `03:30 −07:00` и `01:30 −08:00`, а не исходные 02:30.
- `2020-11-01 01:30` существовало дважды: `01:30 −07:00 = 08:30Z` и `01:30 −08:00 = 09:30Z`. Это два разных момента с одинаковой местной записью.

Для продукта надо отдельно выбрать обработку пропуска и повтора. Принятое правило нескольких ответов для единиц само по себе этого не решает: если отбросить смещение при показе, два момента будут визуально одинаковы, но арифметически различны. Нужны решение о составе отображаемого ответа и согласование с группировкой/копированием.

Правила зон меняются административно. IANA поддерживает базу изменений смещений и переходов и периодически обновляет её. Поэтому сохранённые будущие локальные события и сохранённые точные моменты имеют разные требования при обновлении базы. [IANA Time Zone Database](https://www.iana.org/time-zones). Выбор поставки данных и политики пересчёта остаётся за проектом; проверка ниже не доказывает одинаковость нативных API Windows/macOS.

## Форматы и границы стандартов

RFC 3339 — профиль ISO 8601 для временных меток, а не полный синтаксис календарного калькулятора. Его полная метка содержит дату `YYYY-MM-DD`, `T`, время с секундами и `Z` либо числовое смещение. Дробная часть секунды записывается с точкой; часы ограничены 00–23. Разрешённое значение секунды 60 связано с добавочной секундой и не означает, что любая дата допускает `:60`. Дата должна существовать в своём месяце. RFC не задаёт арифметику длительностей. Одинокие `2026-10-09`, `14:30` и локальная дата со временем без смещения не являются полными метками этого профиля. [RFC 3339, §1, §5.6–5.7](https://www.rfc-editor.org/rfc/rfc3339).

У Temporal есть отдельные машинные записи для даты, времени и других типов, а локализованный вывод отделён от машинного разбора. Политика принятия региональных строк вроде `09.10.2026` не получается автоматически из поддержки ISO-подобного формата. [TC39, String Parsing, Serialization, and Formatting](https://tc39.es/proposal-temporal/docs/strings.html). Полный текст стандарта ISO 8601 в исследовании не изучался; все утверждения выше ограничены открытыми первичными RFC и документацией TC39.

**Вывод для нашего языка:** распознавание `2026-10-09` как даты конкурирует с обычным вычитанием. Стандарты формата данных не решают эту лексическую неоднозначность формулы. Необходимо согласовать, когда дефисы принадлежат дате, как явно написать вычитание и что делать с незавершённой либо несуществующей датой. Также не определены локальные форматы, секунды/доли секунды, диапазон лет, `24:00`, добавочные секунды, точность и текст копирования.

## Динамические значения: что ещё предстоит решить

Из задачи следует потребность в зависимости от текущего времени, но следующие правила пока являются вопросами продукта:

1. Набор значений: сегодня/вчера и, если нужно, завтра/сейчас; латинские и локальные имена. «Сейчас» требует выбора между локальным временем и точным моментом.
2. Зона текущей даты, область настройки и поведение при смене зоны ОС.
3. Единый снимок текущего времени на один пересчёт, чтобы одинаковое имя было согласовано в формуле; частота обновления открытой строки/листа, пробуждение компьютера, полночь.
4. Передача динамической зависимости через пользовательские константы, функции и шаблоны; история сохраняет прежний результат, а повторный вызов формулы может пересчитывать его.
5. Дата ± период; дата − дата; дата + часы; время суток с переходом через полночь; смешение даты без зоны и точного момента. Нужны понятные правила результата и ошибок без скрытой потери даты/часов.
6. Обозначения календарных месяца/года, дробные периоды, порядок применения составного периода, отсутствие автоматической длины месяца в секундах.
7. Поведение конца месяца, gap/fold, формат отображения и копирования даты/времени, совместимость с общими правилами нескольких ответов.

Это список зависимостей для одного полного раунда или нескольких тематических раундов, а не рекомендация принять всё перечисленное в продукт. Библиотека, зона по умолчанию, синтаксис и политика ограничения дат здесь не выбраны.

## Как проверены числовые примеры

Локальное окружение проверки: **Python 3.12.14**, пакет **tzdata 2026.3**, `zoneinfo.TZPATH = ()`, поэтому зональные данные получены из установленного пакета. `zoneinfo` документирует такой источник данных и `fold`; сами конструкторы не служат строгим валидатором несуществующего местного времени. Для gap/fold выполнен обратный перевод через UTC. [Python zoneinfo, Data sources](https://docs.python.org/3/library/zoneinfo.html#data-sources).

Вычисления выполнены временными командами, код приложения и зависимости проекта не изменялись. Проверены: сумма 31 дня; длины февраля; условные примеры ограничения месяца; весенние 23h/24h и осенние 25h/24h; оба UTC-кандидата gap/fold. Минимальный воспроизводимый фрагмент:

```python
from datetime import date, datetime, timedelta, timezone
from calendar import monthrange
from zoneinfo import ZoneInfo

assert date(2026, 10, 9) + timedelta(weeks=4, days=3) == date(2026, 11, 9)
assert [monthrange(y, 2)[1] for y in (2024, 2025, 2026)] == [29, 28, 28]

def illustrative_clamp(d, months):  # условная политика, не реализация продукта
    year, month0 = divmod(d.year * 12 + d.month - 1 + months, 12)
    return date(year, month0 + 1, min(d.day, monthrange(year, month0 + 1)[1]))

assert illustrative_clamp(date(2024, 2, 29), 12) == date(2025, 2, 28)
assert illustrative_clamp(date(2026, 1, 31), 2) == date(2026, 3, 31)
assert illustrative_clamp(illustrative_clamp(date(2026, 1, 31), 1), 1) == date(2026, 3, 28)

zone = ZoneInfo('America/Los_Angeles')
for source in ('2020-03-07T12:00:00', '2020-10-31T12:00:00'):
    start = datetime.fromisoformat(source).replace(tzinfo=zone)
    next_wall_day = start + timedelta(days=1)
    after_24h = (start.astimezone(timezone.utc) + timedelta(hours=24)).astimezone(zone)
    elapsed = next_wall_day.astimezone(timezone.utc) - start.astimezone(timezone.utc)
    print(next_wall_day.isoformat(), elapsed.total_seconds() / 3600, after_24h.isoformat())

for source in ('2020-03-08T02:30:00', '2020-11-01T01:30:00'):
    wall = datetime.fromisoformat(source)
    for fold in (0, 1):
        exact = wall.replace(tzinfo=zone, fold=fold).astimezone(timezone.utc)
        back = exact.astimezone(zone)
        print(source, exact.isoformat(), back.isoformat(), back.replace(tzinfo=None) == wall)
```

Вычитание зональных значений для фактически прошедших часов намеренно выполнено **после перевода обоих в UTC**: операция Python над двумя `datetime` с одним `tzinfo` имеет календарную семантику разности, а не автоматически учитывает изменение смещения. Это поведение описывает [Python datetime, Supported operations](https://docs.python.org/3/library/datetime.html#datetime-objects). Проверки не запускают парсер калькулятора, Temporal или нативные оболочки и не выбирают их для реализации.
