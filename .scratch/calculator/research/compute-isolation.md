# Изоляция вычислений и граница 200 мс

Проверено по первичным источникам 2026-09-14 для вопроса «Изоляция вычислений и принудительная остановка». Контекст: [принятые бюджеты](../distribution/performance.json), [численный контракт](../language/numbers.json), [предыдущее исследование оболочек](shell-and-interop-options.md). Ниже техническая рекомендация для архитектуры, не изменение продуктовых правил и не результат испытания. Ничего не устанавливалось; worker не реализован и не запускался.

## Рекомендуемая граница

Сохранить обычные WPF/AppKit UI, общий управляющий Rust-модуль в процессе оболочки и отдельный Rust-процесс вычислений. Управляющий модуль владеет состоянием запросов, сроками, IPC и перезапуском. Worker получает неизменяемый снимок выражения/листа, определений и контекста; весь потенциально дорогой путь — разбор, зависимости, lazy-решатель, численные алгоритмы и подготовка результата — выполняется там. История, документы и пользовательские определения сохраняются вне worker; вычислитель не пишет пользовательские данные и не создаёт потомков. Это проектное решение для безопасного отбрасывания процесса вместе с его памятью.

Поток в процессе UI не даёт такой границы: Microsoft описывает оставленные блокировки и повреждение общего состояния после `TerminateThread`; Apple также предостерегает от принудительного убийства потоков и рекомендует кооперативную отмену. Если библиотека не опрашивает отмену, контролируемо уничтожать следует вычислительный процесс. [Microsoft: TerminateThread](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-terminatethread), [Apple: Thread Management](https://developer.apple.com/library/archive/documentation/Cocoa/Conceptual/Multithreading/CreatingThreads/CreatingThreads.html).

C ABI остаётся границей **оболочка → управляющий модуль**, а не способом выполнять численную библиотеку в UI-процессе. Рекомендация: непрозрачный дескриптор, UTF-8 с длиной, явное освобождение буфера, версия протокола; короткие вызовы постановки команды и получения событий, без ожидания pipe/worker на UI-потоке. Panic/исключения через обычный C ABI не пропускать: Rust panic на запрещающей unwind границе приводит к abort; `catch_unwind` не ловит abort и не является защитой от зависания. [Rust FFI](https://doc.rust-lang.org/nomicon/ffi.html#ffi-and-unwinding).

## Локальный транспорт и актуальность

Для первой реализации достаточно двух pipe: stdin для команд, stdout для ответов; stderr независимо опустошать в ограниченный диагностический буфер либо отключить. Rust поддерживает `Stdio::piped()` и прямо предупреждает о deadlock, если писать больше ёмкости pipe, не читая одновременно stdout/stderr. Поэтому чтение, запись и watchdog — независимые задачи; никто не держит управляющую блокировку во время блокирующего I/O. [Rust Stdio](https://doc.rust-lang.org/std/process/struct.Stdio.html).

Проектируемый формат — кадр «длина + UTF-8 JSON», с проверяемой версией и размером до выделения памяти; число передаётся десятичной строкой, тип и единица — стабильными идентификаторами. Предельный размер кадра не должен молча обрезать текст или lazy-ответы; большие снимки можно передавать несколькими кадрами. Протокол отделяет `Ready`, запрос, отмену, полностью готовый результат выражения и завершение запроса. EOF посреди кадра — повреждённый ответ, не частичный успех.

Каждая команда/ответ содержит поколение worker, идентификатор документа, ревизию текста/зависимостей и монотонный request ID. Контроллер принимает результат только для текущего набора идентификаторов и незавершённого запроса; UI повторно проверяет актуальность перед применением события. Новая правка немедленно делает предыдущий запрос неактуальным. Полностью полученные независимые результаты листа можно сохранять по принятому контракту, но отдельное выражение готово лишь вместе со **всеми** допустимыми смыслами. Это правила проектируемого протокола, не гарантии pipe или ОС.

## Windows 11

Создать отдельный Job Object для worker, включить `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`, не разрешать breakaway; последний handle Job хранит только управляющий процесс. Закрытие последнего handle завершает связанные процессы; `TerminateJobObject` завершает весь Job. Это также покрывает завершение родителя при корректном владении handle. [Job Objects](https://learn.microsoft.com/en-us/windows/win32/procthread/job-objects), [TerminateJobObject](https://learn.microsoft.com/en-us/windows/win32/api/jobapi2/nf-jobapi2-terminatejobobject).

Для назначения Job непосредственно при создании использовать небольшой Win32-адаптер: `CreateProcessW`, `STARTUPINFOEX`, `PROC_THREAD_ATTRIBUTE_JOB_LIST` и явный список наследуемых pipe handles. Job-list поддерживается с Windows 10; путь к worker передавать явно, без командного интерпретатора. Ошибка настройки/создания означает неуспешный запуск, а не тихий запуск без Job. [CreateProcessW](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-createprocessw), [атрибуты процесса](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-updateprocthreadattribute).

Альтернатива `CREATE_SUSPENDED → AssignProcessToJobObject → ResumeThread` предотвращает вычисление до назначения Job, но оставляет окно между созданием и назначением при аварии родителя. Поэтому предпочтителен Job-list при создании. Для консольного helper предусмотрен `CREATE_NO_WINDOW`. Rust `spawn_with_attributes` пока обозначен nightly-only: обычный стабильный `Command::spawn` не подменяет необходимый Win32-адаптер. [Флаги создания](https://learn.microsoft.com/en-us/windows/win32/procthread/process-creation-flags), [AssignProcessToJobObject](https://learn.microsoft.com/en-us/windows/win32/api/jobapi2/nf-jobapi2-assignprocesstojobobject), [Rust CommandExt](https://doc.rust-lang.org/std/os/windows/process/trait.CommandExt.html#tymethod.spawn_with_attributes).

`TerminateProcess` извне асинхронен: прекращает выполнение потоков, запрашивает отмену I/O; фактический выход ждёт завершения/отмены I/O. Успех вызова не равен подтверждённому выходу. Наблюдать handle процесса и освобождать ресурсы вне UI-потока. [TerminateProcess](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-terminateprocess).

## macOS 14+ и Rust Child

Для единственного worker без потомков достаточно `Child::kill()` — на Unix это SIGKILL — затем `wait()` либо неблокирующий `try_wait()`. `Child` при drop сам не убивает и не ожидает процесс; на Unix ожидание собирает статус и предотвращает zombie. Владение Child и kill/reap сериализовать одним контроллером; не посылать сигнал по сохранённому PID после его освобождения. [Rust Child](https://doc.rust-lang.org/std/process/struct.Child.html).

Apple документирует `kill(pid, SIGKILL)` и `waitpid`; SIGKILL нельзя перехватить, игнорировать или блокировать. Убийство одного PID не означает убийство всех потомков: для группы нужен отдельный механизм, поэтому запрет создавать потомков — осознанное ограничение реализации worker. [Apple kill](https://developer.apple.com/library/archive/documentation/System/Conceptual/ManPages_iPhoneOS/man2/kill.2.html), [sigaction](https://developer.apple.com/library/archive/documentation/System/Conceptual/ManPages_iPhoneOS/man2/sigaction.2.html), [wait](https://developer.apple.com/library/archive/documentation/System/Conceptual/ManPages_iPhoneOS/man2/wait.2.html).

При смерти родителя предложен отдельный управляющий поток worker, продолжающий читать stdin независимо от вычислителя. EOF вызывает завершение всего worker через `_exit`, без ожидания кооперации вычислительного потока. Закрыть лишние копии пишущего дескриптора: EOF приходит только после исчерпания буфера и закрытия писателей. Это не kernel-гарантия срока при зависании самого управляющего потока. Apple отдельно предупреждает, что освобождение дескрипторов при `_exit` может задержать окончательный выход. [Apple pipe](https://developer.apple.com/library/archive/documentation/System/Conceptual/ManPages_iPhoneOS/man2/pipe.2.html), [_exit](https://developer.apple.com/library/archive/documentation/System/Conceptual/ManPages_iPhoneOS/man2/_exit.2.html). Архивные страницы Apple описывают системные вызовы Mac OS X; их наличие не заменяет сборку и прогон на целевых macOS 14/Intel и Apple silicon.

## Отмена, восстановление и три разных срока

Рекомендуемая машина состояний: `starting → idle → running → stopping → exited → starting`. Для новой правки — сначала инвалидировать прежний запрос, затем кооперативная отмена с ограниченным ожиданием внутри оставшегося бюджета; некооперативный worker завершить принудительно. При дедлайне дополнительной отсрочки не давать. Watchdog находится вне worker. До подтверждённого выхода не создавать неограниченную цепь замен: хранить только последний ожидающий снимок. Перезапуск выполняет handshake и загружает актуальный контекст; авария/таймаут не дают старому запросу новый 200-мс бюджет.

Следует различать:

1. **Допуск результата.** Контроллер проверяет elapsed и актуальность при каждом полном ответе, даже если callback таймера ещё не исполнился; просроченный ответ не становится готовым. Начало отсчёта фиксируется до IPC/разбора и не переносится на новую ветку lazy-решателя.
2. **Остановка вычисления.** При обнаружении дедлайна контроллер инвалидирует запрос и инициирует kill. Фактический выход/reap регистрируется отдельным событием; UI его не ждёт.
3. **Планировщик и отрисовка.** Обычная ОС не обещает исполнение watchdog и paint ровно на 200-й миллисекунде. Microsoft описывает вытеснение низких приоритетов и предостерегает от realtime-приоритета; Apple прямо не гарантирует время выполнения повышенным приоритетом. Следствие: точные 200 мс для физической смерти процесса или показанного пикселя обещать нельзя. [Microsoft scheduling](https://learn.microsoft.com/en-us/windows/win32/procthread/scheduling-priorities), [Apple scheduling](https://developer.apple.com/library/archive/documentation/Cocoa/Conceptual/Multithreading/CreatingThreads/CreatingThreads.html#//apple_ref/doc/uid/20001282-BCIDBAHF).

Для elapsed подходит монотонный `Instant`, но включение сна системы в elapsed у Rust зависит от платформы/версии. На sleep/wake следует инвалидировать текущие запросы и отдельно определить повтор; сырой `Instant` не сериализовать между процессами. [Rust Instant](https://doc.rust-lang.org/std/time/struct.Instant.html).

Архитектуре остаётся согласовать поведение после внутренней аварии и неуспешного перезапуска; исследование не выбирает автоматический повтор формулы. Практический следующий тест: зависший численный вызов, заполненный pipe, запоздавший ответ, смерть родителя и повторные аварии; измерить отдельно публикацию, kill, exit/reap, восстановление и суммарную память. Детерминированные ограничения работы дополняют elapsed-guard; молчаливое усечение lazy-ответов и ручной режим долгого ожидания остаются запрещены принятым контрактом.
