# Оболочки и связь с общим ядром: кандидат для прототипа

Проверено 2026-09-12 для [Технологии оболочек и связи с общим ядром](../issues/22-shell-and-interop-options.md). Контекст: [предыдущее исследование](platform-capabilities.md). Цели уже приняты: Windows 11 x64; macOS 14+ Intel/Apple silicon; 150 MB в скрытом фоне и 250 MB с открытым листом суммарно по собственным процессам; теплый вызов 100 мс, обычный ответ 50 мс, пересчет до 200 мс, старт до 2 с; целевой класс 8 GB/SSD. Это требования, а не результаты измерений. Утвержденное оформление сохраняется. Вычислительные библиотеки здесь не рассматриваются.

## A. Rust + WPF на Windows и Swift/AppKit на Mac

**Windows.** WPF работает только на Windows и предоставляет `AllowsTransparency=true` при `WindowStyle=None`: это документированный путь к прозрачному окну произвольной формы. Одного прозрачного `Background` недостаточно. Для данной палитры такой механизм дает конкретную исходную точку без выбора нового оформления. [WPF](https://learn.microsoft.com/en-us/dotnet/desktop/wpf/overview/), [AllowsTransparency](https://learn.microsoft.com/en-us/dotnet/api/system.windows.window.allowstransparency).

WinUI 3 — общая рекомендация Microsoft для новых Windows-приложений; он входит в Windows App SDK и поддерживает Windows 11. `OverlappedPresenter.SetBorderAndTitleBar(false, false)` убирает рамку и заголовок. При этом запрос на полноценный прозрачный фон в официальном репозитории остается открытым. Это основание отдельно проверять альфа-прозрачность конкретной версии WinUI, а не объявлять ее невозможной. Для первого эксперимента WPF имеет более прямую документированную опору. [WinUI 3](https://learn.microsoft.com/en-us/windows/apps/winui/winui3/), [Border/title bar](https://learn.microsoft.com/en-us/windows/windows-app-sdk/api/winrt/microsoft.ui.windowing.overlappedpresenter.setborderandtitlebar), [Запрос #1247](https://github.com/microsoft/microsoft-ui-xaml/issues/1247).

WPF `TextBox` редактирует простой текст, `RichTextBox` — форматируемый `FlowDocument`; оба имеют стандартные команды редактирования. `TextBox` предоставляет AutomationPeer, тогда как произвольный рисунок на `Canvas` не получает такую семантику автоматически. Предложение: сохранить системный текстовый ввод и отдельно проверить подсветку, результаты возле строк, выделение и undo в принятом UI. [Текстовые контролы](https://learn.microsoft.com/en-us/dotnet/desktop/wpf/controls/textbox), [UI Automation](https://learn.microsoft.com/en-us/dotnet/desktop/wpf/controls/ui-automation-of-a-wpf-custom-control).

**macOS.** AppKit предоставляет `NSPanel`, стиль `nonactivatingPanel`, прозрачность через свойства окна и `NSTextView` для редактирования. Borderless-окно не становится key/main без соответствующего `canBecomeKey`/`canBecomeMain`; для ввода это существенное условие. `NSTextInputClient` описывает взаимодействие с системой ввода, включая marked text; стандартные AppKit-контролы уже предоставляют основу accessibility. Следовательно, сохранение ввода и доступности нужно проверять при настройке собственного вида палитры. [Borderless](https://developer.apple.com/documentation/appkit/nswindow/stylemask-swift.struct/borderless), [Nonactivating panel](https://developer.apple.com/documentation/appkit/nswindow/stylemask-swift.struct/nonactivatingpanel), [Прозрачность](https://developer.apple.com/documentation/appkit/nswindow/isopaque), [Текстовый ввод](https://developer.apple.com/documentation/appkit/nstextinputclient), [Accessibility](https://developer.apple.com/documentation/appkit/nsaccessibilityprotocol).

**Связь с Rust.** Rust поддерживает `cdylib` для загрузки из другого языка и `staticlib` для включения в приложение. C# вызывает C-интерфейс через P/Invoke (`LibraryImport`); Swift импортирует функции из C-заголовков. Возможный эксперимент: Rust DLL для WPF и Rust static library для AppKit, с одним версионируемым C ABI. [Rust linkage](https://doc.rust-lang.org/reference/linkage.html), [.NET P/Invoke](https://learn.microsoft.com/en-us/dotnet/standard/native-interop/pinvoke), [Swift/C](https://developer.apple.com/documentation/swift/using-imported-c-functions-in-swift).

Предложение для границы: непрозрачные дескрипторы, буфер UTF-8 с длиной, явная функция освобождения, определенные коды ошибок. Владение памятью, время жизни callback, координаты текстовых диапазонов и поведение panic/исключений требуют контракта; обычный Rust ABI и Rust `String` не следует выдавать за C-интерфейс. [Rust FFI](https://doc.rust-lang.org/nomicon/ffi.html). Цена A — две реализации редактора и два адаптера; общий вычислительный код сам по себе не синхронизирует их поведение.

## B. Rust/Tauri 2 + общий HTML/CSS-редактор

Tauri запускает Rust core и WebView-процессы: на Windows используется WebView2/Chromium, на macOS — системный WKWebView/WebKit. Библиотека WebView обычно не включается в исполняемый файл приложения. Поэтому общий HTML/CSS уменьшает дублирование интерфейса, но не устраняет различия движков, их версий и процессов. [Процессы Tauri](https://v2.tauri.app/concept/process-model/), [WebView](https://v2.tauri.app/reference/webview-versions/).

Rust-ядро можно подключить непосредственно как crate; отдельный C ABI между ним и Tauri не обязателен. Веб-редактор вызывает Rust commands через `invoke`; аргументы/результаты сериализуются. Документация рекомендует асинхронные команды для тяжелой работы; обычные синхронные команды по умолчанию выполняются на главном потоке. Планирование CPU-работы и отбрасывание устаревших результатов остаются задачами реализации. [Calling Rust](https://v2.tauri.app/develop/calling-rust/).

Есть настройки окна без декораций, прозрачности и фокуса, а также официальный global-shortcut plugin. На macOS прозрачность требует `macos-private-api`; документация прямо предупреждает о несовместимости этого режима с приемом в App Store. Утвержденная прямая поставка не снимает необходимости проверять такой путь на выбранных macOS. Поведение панели, Spaces/fullscreen и возврат фокуса может потребовать собственных нативных адаптеров. [Конфигурация](https://v2.tauri.app/reference/config/), [Global shortcut](https://v2.tauri.app/plugin/global-shortcut/). Точность оформления, IME и VoiceOver/Narrator общего редактора проверяются на обоих движках.

## Общие ограничения и архитектуры

На Windows `RegisterHotKey` может отказать при конфликте, а `SetForegroundWindow` ограничен системой. На macOS активация является запросом, который ОС может отклонить. Глобальный `NSEvent`-монитор не подавляет события и требует accessibility-доверия для наблюдения клавиатуры; это не эквивалент регистрации одного сочетания. В текущем исходнике Tauri `global-hotkey` на Mac применяется `RegisterEventHotKey`. [Windows hotkey](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-registerhotkey), [Windows focus](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-setforegroundwindow), [Apple activation](https://developer.apple.com/documentation/appkit/passing-control-from-one-app-to-another-with-cooperative-activation), [NSEvent](https://developer.apple.com/library/archive/documentation/Cocoa/Conceptual/EventOverview/MonitoringEvents/MonitoringEvents.html), [Исходник hotkey](https://github.com/tauri-apps/global-hotkey/blob/dev/src/platform_impl/macos/mod.rs).

Нужные Rust targets существуют: `x86_64-pc-windows-msvc`, `x86_64-apple-darwin`, `aarch64-apple-darwin`. Текущая документация относит Intel macOS к Tier 2, Apple silicon к Tier 1; одинаковую степень проверки самим проектом Rust предполагать нельзя. Для macOS надо согласовать deployment target 14 у оболочки, ядра и зависимостей; Tauri имеет `minimumSystemVersion`. [Rust targets](https://doc.rust-lang.org/rustc/platform-support.html), [Apple targets](https://doc.rust-lang.org/rustc/platform-support/apple-darwin.html), [Tauri deployment target](https://v2.tauri.app/distribute/macos-application-bundle/).

Electron, для дополнительного сравнения, включает Chromium и Node.js в свою поставку и использует main/renderer-процессы. Состав поставки отличается от Tauri; из этого не следует конкретный расход RAM или нарушение наших бюджетов. [Electron](https://www.electronjs.org/docs/latest/), [Процессы](https://www.electronjs.org/docs/latest/tutorial/process-model).

## Локальная проверка и рекомендация

Read-only проверка обнаружила .NET SDK **9.0.317**, WindowsDesktop runtimes 8/9/10 и Node **24.19.0**. `cargo`/`rustc` отсутствуют в PATH и стандартной `.cargo/bin`; `cl` отсутствует в PATH, `vswhere` не нашел компонент `VC.Tools.x86.x64`. Ничего не устанавливалось. Подключенная Mac-среда в доступной конфигурации не указана; Mac-сборки не проверялись.

**Рекомендация исследователя: первым испытать A с WPF/AppKit и узким C ABI.** Причина — прямые средства прозрачного окна и системного ввода; соответствие памяти пока неизвестно. B сохраняется кандидатом, если стоимость двух редакторов окажется чрезмерной. Это выбор эксперимента, не production-стека.

Прототип должен воспроизвести одобренный UI, немедленный ввод после hotkey, выделение/IME/undo, доступность, скрытие и возврат фокуса, DPI/Spaces/fullscreen. Затем измерить принятые бюджеты в release-сборке на целевом классе оборудования, включая все относящиеся к приложению вспомогательные процессы. Наличие API, локального SDK или браузерного макета не заменяет эти проверки.
