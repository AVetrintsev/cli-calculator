# Механизмы подписанной установки и обновления

Дата проверки: **2026-09-15**. Вопрос 33; основание — принятые [правила поставки](../distribution/policy.json) и [архитектура](../architecture/proposal.md). Это исследование для спецификации. Установщики, сертификаты, учётные записи, публикация и испытания готовых пакетов не выполнялись. Проверены первичные документы и исходники; ссылки на ветку Sparkle `2.x` описывают просмотренное состояние, а не закреплённую зависимость продукта.

## Предлагаемый инженерный выбор и его границы

**Инженерный вывод: для Windows приоритетно рассмотреть MSIX/App Installer с тихой проверкой внутри приложения и явной системной установкой после persist; для macOS — Sparkle 2, универсальный .app в подписанном и нотариализованном DMG.** Это рекомендации по совокупности приведённых ниже фактов, а не результаты испытаний. Системная проверка подписанного MSIX и документированная атомарность пакетных операций дают более сильное основание для безопасной замены, чем просмотренный путь Velopack. Точный сценарий установки/перезапуска MSIX и сохранение внешнего хранилища ещё требуют проверки готового пакета.

**Velopack — рассмотренная альтернатива, не признанная соответствующей всем гарантиям.** У него прямой документированный путь WPF/per-user Setup.exe и управляемый API, но при неудачной замене возможна неработоспособная установка. Простота интеграции не устраняет эту границу. Его можно выбирать только с явно записанным и проверенным repair/reinstall-сценарием; обязательный автоматический возврат старой программы при любом сбое этот механизм не обеспечивает.

Ни один вариант не доказывает сквозную атомарность «программа + SQLite + рабочее состояние». Автоматический перезапуск и восстановление состояния при следующем успешном запуске проверяются отдельно: ограничение первого не означает разрешение терять второе.

## Windows: Velopack, документированные возможности

| Область | Факт и следствие для спецификации |
| --- | --- |
| WPF и x64 | Официальное руководство содержит отдельную интеграцию WPF через ранний `VelopackApp.Build().Run()` в собственном `Main` и пример self-contained `win-x64`. Это подтверждает поддерживаемый способ интеграции; AvalonEdit, Rust DLL, worker и SQLite конкретного калькулятора им не испытаны. [C#/WPF](https://docs.velopack.io/getting-started/csharp). |
| Windows 11 | Velopack понимает ограничения ОС/архитектуры в RID; документация отдельно объясняет Windows 11 как версию Windows 10 с build не ниже 22000. Задать принятую нижнюю границу установщику отдельно от компиляции x64. RID не доказывает, что все включённые бинарные зависимости запустятся. [Runtime/OS](https://docs.velopack.io/packaging/runtime). |
| Установка без администратора | `Setup.exe` устанавливает в `%LocalAppData%\{packId}` без elevation. Каталог `current` заменяется при обновлении; корневой execution stub обеспечивает стабильный путь запуска. Использовать обычную per-user конфигурацию. [Windows layout](https://docs.velopack.io/packaging/operating-systems/windows). |
| Зависимости и офлайн | Self-contained .NET не требует установки общего .NET runtime. Velopack умеет загружать и устанавливать prerequisites, включая при обновлении. Поэтому предложение — включать необходимые runtime/native-компоненты в пакет и не вводить обязательный системный bootstrap; отдельно проверить зависимости Rust/SQLite. Self-contained .NET сам по себе не доказывает отсутствие любых prerequisites. [Bootstrapping](https://docs.velopack.io/packaging/bootstrapping). |
| Проверка/установка | `CheckForUpdatesAsync`, `DownloadUpdatesAsync` и `ApplyUpdatesAndRestart` разделены. Автоматический таймер вызывает только проверку; доступность/сбой отражаются в меню. Пользовательская команда запускает дальнейший путь. `SetAutoApplyOnStartup(false)` обязателен: применение уже загруженных обновлений при старте включено по умолчанию. [C#](https://docs.velopack.io/getting-started/csharp), [VelopackApp](https://docs.velopack.io/reference/cs/Velopack/VelopackApp). |

`ApplyUpdatesAndRestart` немедленно завершает вызывающее приложение. Успешное сохранение текущих ревизий, рабочего состояния и остановка worker с освобождением SQLite/native DLL должны завершиться **до** вызова. `WaitExitThenApplyUpdates` тоже уже запускает установщик, ожидающий выхода; это не барьер, который можно безусловно отменить при поздней ошибке сохранения. [UpdateManager](https://docs.velopack.io/reference/cs/Velopack/UpdateManager).

FastCallback/hooks установки не подходят для обязательного сохранения или миграций: имеют жёсткий тайм-аут, не могут отменить установку и не допускают своего UI; зависший обработчик завершается принудительно. Обновление также может убить процессы из `current`, пытаясь снять блокировку. Наш worker должен штатно остановиться раньше, а не надеяться на это поведение. [Hooks](https://docs.velopack.io/integrating/hooks), [Windows updating](https://docs.velopack.io/packaging/operating-systems/windows).

**Подпись и доверие — разные проверки.** В процессе `vpk pack` подписывать наши EXE/DLL, Setup, Update и создаваемые stub-файлы подходящей доверенной Authenticode-подписью с timestamp; Velopack предоставляет `--signParams`/`--signTemplate` для этапов упаковки. Не изменять подписанные файлы после подписи. Подпись не гарантирует отсутствие SmartScreen: утверждение страницы Velopack об «instant reputation» для EV противоречит актуальному владельцу поведения — Microsoft прямо говорит, что EV больше не обходит SmartScreen. [Signing integration](https://docs.velopack.io/packaging/signing), [Microsoft SmartScreen](https://learn.microsoft.com/en-us/windows/apps/package-and-deploy/smartscreen-reputation).

В просмотренном `UpdateManager` тега **1.2.0** проверяется размер и SHA-256 пакета из feed, с fallback на SHA-1; после загрузки извлекается новый `Update.exe`. Этот путь не содержит проверки подписи издателя пакета. Следовательно, подпись Setup/EXE и checksum из того же HTTPS-feed **нельзя выдавать за независимую аутентификацию обновления при компрометации feed**. Публикация по HTTPS и проверка подписей выпуска обязательны, а заявлять защиту от подмены feed можно лишь после отдельного подтверждения механизма проверки до извлечения updater. Собственный криптографический updater здесь не проектируется. [Просмотренный код](https://raw.githubusercontent.com/velopack/velopack/1.2.0/src/lib-csharp/UpdateManager.cs).

## macOS: совместимость, DMG и управление Sparkle

Документация Sparkle заявляет **macOS 12+** и работу с Cocoa-приложениями. Просмотренная конфигурация `2.x` задаёт deployment target 12.0 и `ARCHS_STANDARD`, явно упоминая возможность удалить `x86_64`. Apple описывает стандартную universal-сборку с `x86_64` и `arm64`. Это документированное основание применимости к macOS 14 Intel и Apple silicon, **не результат нашей сборки или запуска**. Для выпуска необходимо проверить оба среза в оболочке, Rust-библиотеке, worker и всех встроенных frameworks/helpers; deployment target всех компонентов должен допускать macOS 14. [Sparkle support](https://sparkle-project.org/), [Конфигурация](https://github.com/sparkle-project/Sparkle/blob/2.x/Configurations/ConfigCommon.xcconfig), [Apple universal binaries](https://developer.apple.com/documentation/apple-silicon/building-a-universal-macos-binary).

Предлагается один universal `.app` и DMG; appcast ограничивает выпуск macOS `14.0.0`, без arm64-only hardware requirement. Sparkle поддерживает DMG как архив обновления, поэтому тот же готовый образ можно использовать для прямой загрузки и обновления. Установка — копирование .app из образа в доступное пользователю расположение. Из read-only DMG или при translocation обновление может быть недоступно; это нужно показать при ручной попытке. Если приложение принадлежит другому пользователю либо находится в защищённом месте, Sparkle может попросить администратора; пользовательское расположение, например `~/Applications`, сохраняет принятый путь без обязательного администратора. [Appcast requirements](https://sparkle-project.org/documentation/api-reference/Classes/SUAppcastItem.html), [DMG distribution](https://sparkle-project.org/documentation/), [Authorization](https://sparkle-project.github.io/documentation/custom-user-interfaces/).

Для прямой поставки: Developer ID Application, корректная подпись вложенного исполняемого кода, Hardened Runtime и secure timestamp; notarization через поддерживаемый Apple workflow. Подписанный .dmg не заменяет подпись .app. Приложить нотариальные tickets к распространяемым app/DMG, чтобы Gatekeeper мог найти ticket без сети. Developer ID Installer нужен для installer-package, которого выбранная схема .app/DMG не требует. [Apple notarization](https://developer.apple.com/documentation/security/notarizing-macos-software-before-distribution?language=objc), [Требования подписи](https://developer.apple.com/documentation/Security/resolving-common-notarization-issues), [Stapling](https://developer.apple.com/documentation/security/customizing-the-notarization-workflow).

Дополнительно Sparkle использует собственную **EdDSA/Ed25519-подпись итогового архива** и встроенный `SUPublicEDKey`, HTTPS-feed в `SUFeedURL`; Apple-подпись и EdDSA решают разные задачи. Подписывать окончательные байты архива, после всех изменений и stapling. Хранить ключ отдельно от хостинга. При ротации сохранять доверенную цепочку: документация допускает изменение Apple signing identity или EdDSA key по отдельности, но не обоих одновременно. [Sparkle security](https://sparkle-project.org/documentation/).

Для принятой политики задать `SUEnableAutomaticChecks=YES`, `SUAutomaticallyUpdate=NO`, **`SUAllowsAutomaticUpdates=NO`**; пользовательская настройка меняет `automaticallyChecksForUpdates`, а не принудительно переустанавливается при каждом старте. `SUVerifyUpdateBeforeExtraction=YES` предлагается для проверки EdDSA до распаковки; при последующей ротации EdDSA это требует Developer-ID-подписанного DMG. [Configuration](https://sparkle-project.org/documentation/customization/).

Обычная фоновая проверка Sparkle может показать окно доступного обновления. Готовые Gentle Reminders позволяют заменить **все** scheduled alerts, включая immediate-focus случаи, индикатором меню. Для точного барьера сохранения инженерно предпочтителен собственный `SPUUserDriver` поверх готового Sparkle: он показывает принятый индикатор, явную команду установки, прогресс и ошибки. Это адаптер интерфейса, не собственный алгоритм замены программы. Альтернативный API `checkForUpdateInformation` только сообщает о наличии обновления и не предлагает установить его. [Gentle Reminders](https://sparkle-project.org/documentation/gentle-reminders/), [User driver](https://sparkle-project.github.io/documentation/custom-user-interfaces/), [Probing API](https://sparkle-project.org/documentation/api-reference/Classes/SPUUpdater.html).

**Критический порядок Sparkle:** команду установки привязать к актуальному выпуску; сохранить/заморозить рабочее состояние **до передачи первого ответа Install, начинающего загрузку и подготовку установки**. После подготовки приложение может обновиться при собственном выходе, даже без финального relaunch-диалога. Поэтому одно `shouldPostponeRelaunchForUpdate` недостаточно: документация перечисляет случаи, когда оно не вызывается. В `showReadyToInstallAndRelaunch` ответ Dismiss также оставляет возможность установки на выходе; для отмены подготовленного обновления нужен Skip — в этом состоянии он отменяет текущую установку, не исключая версию навсегда. Размораживать правки после отказа можно только после отмены/разоружения подготовленной установки. [User-driver contract](https://sparkle-project.org/documentation/api-reference/Protocols/SPUUserDriver.html), [Relaunch delegate](https://sparkle-project.org/documentation/api-reference/Protocols/SPUUpdaterDelegate.html).

## Windows: MSIX/App Installer

- **Применимость:** WPF можно упаковать в MSIX; установка пакета per-user. Для публичной прямой поставки пакет подписан доверенным сертификатом, чьё имя совпадает с `Publisher`; системный механизм проверяет подпись и block map. [WPF packaging](https://learn.microsoft.com/en-us/windows/apps/desktop/modernize/dotnet/package-app), [Package layout](https://learn.microsoft.com/en-us/windows/msix/desktop/desktop-to-uwp-behind-the-scenes), [Signing](https://learn.microsoft.com/en-us/windows/msix/package/sign-app-package-using-signtool), [MSIX integrity](https://learn.microsoft.com/en-us/windows/msix/overview).
- **Личные данные сохраняемы:** на Windows 11 можно объявить конкретный внешний каталог AppData через `ExcludedDirectories` и `unvirtualizedResources`. Документация прямо связывает это с сохранением после uninstall. Нельзя оставлять единственную базу в управляемом package app-data или рассчитывать, что обычный путь AppData автоматически исключает виртуализацию. [Flexible virtualization](https://learn.microsoft.com/en-us/windows/msix/desktop/flexible-virtualization).
- **Ручная установка достижима:** не включать автоматические `OnLaunch`/`AutomaticBackgroundTask` и блокирующее запуск обновление. Собственный тихий планировщик может вызывать `Package.CheckUpdateAvailabilityAsync`; установка вызывается отдельным `PackageManager` API после нашего persist. `CheckUpdateAvailabilityAsync` требует установки через .appinstaller. `ForceTargetAppShutdown` закрывает целевой пакет, поэтому это только действие после барьера. [Update settings](https://learn.microsoft.com/en-us/windows/msix/app-installer/auto-update-and-repair--overview), [APIs](https://learn.microsoft.com/en-us/windows/msix/app-installer/app-installer-documentation), [Shutdown option](https://learn.microsoft.com/en-us/uwp/api/windows.management.deployment.addpackagebyappinstalleroptions?view=winrt-26100).
- **Граница надёжности:** Microsoft документирует атомарность добавления приложения вместе с optional packages. Это основание предпочесть системную пакетную операцию при дальнейшей оценке, но не доказательство автоматического отката после запуска новой версии или изменения SQLite. Relaunch также требует проверки: `RegisterApplicationRestart` ограничен условиями, в том числе минимумом 60 секунд работы процесса. Переходить на MSIX исключительно на основании слова «атомарность» преждевременно. [Atomic deployment example](https://learn.microsoft.com/en-us/powershell/module/appx/add-appxpackage?view=windowsserver2025-ps), [Restart requirements](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-registerapplicationrestart).

## Отказ, возврат и миграции данных

| Момент сбоя | Что допустимо утверждать и требовать |
| --- | --- |
| Проверка/загрузка/проверка целостности | Требование интеграции: установленная оболочка и общий вычислитель остаются доступны офлайн; личные данные не меняются установщиком. Сбой отражается в меню или уже открытом по команде пользователя прогрессе, без повторяющихся фоновых модальных сообщений. Неудачная загрузка не становится разрешением на установку при следующем старте. |
| Сохранение, backup, остановка worker | Требование интеграции: при ошибке не передавать управление установке; не терять несохранённый текст. Успех означает завершённый persist, а не постановку записи в очередь. После разрешения установки не принимать новые несохранённые изменения. |
| Замена файлов Velopack | Просмотренный `apply_windows_impl.rs` 1.2.0 перемещает `current` во временный каталог, затем новую версию в `current`. При сбое второго перемещения возможна broken installation; cleanup удаляет временные каталоги. Это **не гарантированный rollback**. При некоторых блокировках документация обещает отказ и запуск старой версии, но нельзя распространять это на все сбои. [Код замены](https://raw.githubusercontent.com/velopack/velopack/1.2.0/src/bins/src/commands/apply_windows_impl.rs), [Блокировки](https://docs.velopack.io/packaging/operating-systems/windows). |
| Замена файлов Sparkle | `SUPlainInstaller` пытается атомарно обменять .app при подходящих условиях; fallback перемещает старую программу и пытается вернуть её, если помещение новой не удалось. Возврат сам может не удаться. Это операция с bundle, без проверки здоровья новой программы и без отката SQLite. [Код установщика](https://raw.githubusercontent.com/sparkle-project/Sparkle/2.x/Autoupdate/SUPlainInstaller.m). |
| Приложение заменено, запуск/миграция неуспешны | Проверенная повторная установка подписанного полного пакета — явный сценарий восстановления самой программы. Она не очищает и не заменяет пользовательское хранилище. Старую версию можно использовать только с совместимой схемой; Sparkle дополнительно запрещает downgrade bundle в обычном update flow. Для исправления дефектного выпуска обычный канал может доставить исправленную совместимую программу с возрастающим номером. [Sparkle installer](https://raw.githubusercontent.com/sparkle-project/Sparkle/2.x/Autoupdate/SUPlainInstaller.m). |

Миграциями владеет общий модуль хранения **после запуска новой программы**, не installer hook. Принятый контракт требует защитного согласованного снимка, изменения данных и номера схемы одной транзакцией, сохранения исходника при неуспехе и запрета записи неизвестной схемы старой программой. Ошибка миграции не означает разрешения восстановить старый backup поверх новых пользовательских изменений. Возврат программы и восстановление выбранного снимка — разные операции; сохраняются их уже принятые правила. [Архитектура хранения](../architecture/proposal.md), [SQLite migration procedure](https://www.sqlite.org/lang_altertable.html#making_other_kinds_of_table_schema_changes), [Backup/WAL](https://www.sqlite.org/backup.html).

На Windows вся личная база, поколения, настройки и десять резервных снимков должны находиться **вне всего `RootAppDir` Velopack**, не только вне `current`; поддерживаемый пример — `%AppData%\{packId}` либо отдельный стабильный пользовательский каталог, который uninstall не удаляет. На Mac — вне .app/DMG, в постоянном пользовательском хранилище. Удаляется программа и её системная регистрация, но не исходные данные. Повторная установка использует тот же идентификатор данных. [Velopack preservation](https://docs.velopack.io/integrating/preserved-files), [Uninstall scope](https://docs.velopack.io/integrating/uninstalling), [Принятая политика](../distribution/policy.json).
