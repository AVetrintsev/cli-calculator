## Question

Для каждого сценария записать фактическое состояние исходной базы, незавершённого действия и резервного файла; отличить подтверждённый успех записи от попытки её выполнить. Подтвердить, какие технические механизмы достаточны для уже принятых правил сохранности данных, и зафиксировать непроверенные границы.

### Подтверждённые механизмы

- Rust 1.98.1 / rusqlite 0.40.2 собран со встроенной SQLite 3.53.2. Прочитаны source ID и WAL/FULL/foreign_keys/NORMAL/autocheckpoint=1000. C-зависимость собрана локальным Zig 0.15.2; версии, хеши и wrapper сохранены в первичной ветке. Глобальной установки нет.
- Предметная транзакция вместе меняет документ, опубликованное определение, историю и квитанцию. При kill до COMMIT в WAL уже было 2 109 472 байта неподтверждённых страниц; после фактического выхода и повторного открытия сохранилось прежнее состояние. При kill после COMMIT до подтверждения запись остаётся; явный технический повтор того же ID не создаёт дубликат. Принятое правило нового сеанса и запрет автоматического повторения clipboard не меняются.
- Реальные SQLITE_FULL, BUSY и READONLY не приводят к частичной записи или сбросу базы. FULL получен через ограничение страниц при INSERT, не при COMMIT/синхронизации. Смерть отдельного compute-only процесса не прекращает транзакцию владельца хранения; полная интеграция с worker этим не проверена.
- Backup API сохраняет изменения из WAL; копирование одного db теряет новую ревизию в отрицательном контроле. Закреплённая read-транзакция даёт целый снимок, даже если другой writer подтверждает следующую ревизию между шагами backup. Только Done допускает дальнейшую проверку; прерванный More оставляет неопубликованный `.partial`.
- Реальные ошибки Win32 sync (неправильный read-only handle) и публикации (отсутствие share-delete) не заменяют прежний исправный снимок. Десять старых копий не сокращаются после неудачной новой; удаление старейшей следует за публикацией одиннадцатой. Это проверка API, не модели повреждения диска.
- Версию нельзя определять по одному db-header или immutable: они показывают 1 при подтверждённой в WAL версии 999. Для побайтовой защиты оригинала сначала получить единоличное владение и скопировать весь quiescent комплект, затем читать копию обычным SQLite. Исходная семья совпала побайтно до/после проверки. Межпроцессное владение в продукте ещё нужно реализовать; паузы своей очереди недостаточно.
- Защитный backup предшествует миграции; DDL, данные и версия меняются одной транзакцией. Kill до COMMIT и SQL-ошибка оставляют прежнюю схему и копию. Ошибка обязательной защиты запрещает начало миграции.
- Восстановление проверено через отдельные поколения: оригинальная семья остаётся на прежнем месте; выбранный снимок проверяется/мигрируется под новым путём, затем переключается один синхронизированный указатель. До переключения kill сохраняет старый указатель, после успешного возврата — новый. Повреждённый db и его синтетический повреждённый WAL защищены побайтно. Такой комплект не считается исправным backup; при читаемом источнике сохраняется также обязательный согласованный backup последних данных.
- История не зависит от живого определения. Коэффициент из 30 цифр и несколько смыслов сохраняются текстом, без SQLite REAL.
- На Windows нужен явный `win32-longpath` вместе с канонической расширенной формой пути. На 374 символах стандартный VFS дал CANTOPEN, проверенный путь успешно сохранил и опубликовал backup. Ошибка пути не означает повреждение базы.

### Ограничения

Последний прогон — 19:54:47.947 UTC, PID 24036, Windows build 26200; оставшихся процессов 0. Системный буфер и пользовательские базы не использовались. Ранние неудачные прогоны и исправления фикстуры/длинного пути сохранены в README и отчётах.

Process kill не проверяет отключение питания, сбой накопителя или обрыв внутри MoveFileEx. Mac/APFS/fullfsync, полный SQL/импорт, конкурентные ревизии и единственный владелец, обслуживание временных файлов после перезапуска, весь UI и нагрузочные объёмы не проверены. Backup Busy/Locked и его собственный deadline не воспроизведены; BUSY транзакции проверен отдельно. Минимальная схема достаточна для механизма, но не заменяет контракт всех данных. Бюджет вычисления 200 мс не изменён и не подтверждён.

Техническая предпосылка хранения снята. В архитектуре остаются Mac-путь, настоящий составной ввод и явное уточнение временного контракта по уже полученным замерам. Пользователь разрешил переходить к следующей предпосылке без отдельного «продолжай».
