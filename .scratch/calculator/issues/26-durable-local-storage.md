## Question

Подходит ли SQLite как общее локальное хранилище для уже согласованных листов, шаблонов, определений, черновиков и неизменных снимков истории? По первичным источникам проверить атомарные транзакции, режим записи/синхронизации и ограничения гарантий, согласованную резервную копию, смену схемы с возможностью восстановления и границу базы/переносимого пакета. Учесть отсутствие общей транзакции с системным буфером, исключение истории из переносимого экспорта, полный резервный снимок и сохранность при ошибке записи. Не предлагать новую политику хранения/облако и не считать исследование выполненной приёмкой.

## Answer

[Исследование](../research/durable-local-storage.md) завершено по первичным источникам. SQLite подходит для принятых правил: одна база, единственный владелец записи вне вычислительного worker, предметные команды в транзакциях, согласованный backup через Backup API. Рекомендованный кандидат — `rusqlite 0.40.2`, bundled SQLite `3.53.2`, WAL/FULL, foreign_keys; на macOS fullfsync. Зафиксированная исправленная версия необходима с учётом опубликованного WAL-reset bug старых версий.

Числа и типизированные снимки нельзя сводить к REAL/64-битному INTEGER. Полный резервный SQLite-снимок включает историю; переносимый UTF-8 JSON отделён от внутренней схемы и исключает историю/параметры устройства по принятому правилу. Перед миграцией требуется защитная копия; неизвестная новая схема не открывается старой программой для записи. Общей транзакции с системным буфером нет: рекомендованы история с уникальным confirmationId, затем копирование и явное подтверждение успеха оболочкой.

Гарантии зависят от действительного успеха синхронизации ОС/накопителем; запись, восстановление, сбои диска и миграции ещё требуют испытаний. Это технические рекомендации, а не новая политика хранения и не выполненная приёмка. Первичный материал: ветка `codex/research-local-storage`, коммит `948c5acfe1c367adbca1af31f5fbcaac8c5657a4`; основной проект хранит копию отчёта.
