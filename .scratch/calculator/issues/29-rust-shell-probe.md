## Question

Выполнить согласованный пользователем ограниченный сквозной прототип: настоящий WPF-ввод → C ABI общего Rust-модуля сеанса → отдельный вычислительный процесс Rust → ответ в окне. Проверить настоящий расчёт, смену формулы без показа устаревшего ответа, остановку и внутреннюю аварию вычисления с сохранением текста и возможностью следующего расчёта. Измерить путь запроса, обработку UI и фактический выход процессов отдельно. Результат должен дать фактическую основу для [Общее ядро и платформенные оболочки](09-shared-core-and-shells.md).

## Context

Пользователь поручил выполнить этот эксперимент после рекомендации ask-matt. Это AFK-техническая предпосылка, а не новое согласование поведения или реализация всего приложения. Принципы prototype: одноразовый код, состояние видно, один запуск, память вместо пользовательской базы, первичный материал на отдельной ветке. Нативная WPF/Rust-связь необходима по вопросу; HTML-имитация не проверила бы её.

Использовать уже проверенные численный слой и Windows Job/pipe-механизм, зафиксировав происхождение. Проверка не должна затрагивать открытый пользовательский NativePaletteProbe, его горячую клавишу, буфер или данные. Ввод коротких арифметических формул достаточен для пути; весь согласованный язык, редактор/IME/Undo, локализация, хранение и macOS остаются отдельными предпосылками/приёмкой. Принятый предел 200 мс сохраняется: срок допуска ответа и физическое завершение процесса нельзя выдавать друг за друга.

## Answer

Согласованный сквозной эксперимент выполнен: **16/16 сценариев прошли**, дополнительно успешна проверка cleanup с отказом первой попытки destroy и явным повтором. Release-сборка без ошибок/предупреждений: Windows 11 x64 build 26200, .NET SDK 9.0.317 / runtime 9.0.20, Rust/Cargo 1.98.1 GNU x64, Dashu 0.6.0. Зависимости закреплены, первичный код и наблюдения сохранены отдельно.

Фактический путь: WPF TextChanged → копирование UTF-8 через C ABI → очередь/ревизии/срок в Rust DLL → независимые pipe writer/reader → Rust worker с настоящей арифметикой → проверка актуальности в Rust → PostMessage → drain → применение состояния к WPF. Оболочка не вычисляет формулу и не выбирает актуальный ответ самостоятельно. Весь опыт ограничен небольшим арифметическим parser; неизменяемые определения, все типы/lazy и полный редактор этим результатом не подтверждаются.

Проверены обычные ответы (`2 + 2`, десятичные дроби, скобки, 30-значное целое), незавершённый/ошибочный ввод и UTF-8 round-trip. Ответ, уже лежащий в очереди Rust, отброшен после новой правки; 40 быстрых изменений завершились показом только последнего актуального ответа. Ответ worker с неверной ревизией не стал готовым. Аварийный выход, зависание, поздний ответ, оборванный кадр и заполненные stdin/stdout не лишили окно возможности обрабатывать события; текст сохранялся, новая правка давала правильный расчёт. Автоматический повтор упавшего запроса отсутствовал.

Найдено и проверено существенное требование остановки: неуспех native stop запрещает замену worker и освобождение владения. Счётчик остановленных и новый процесс разрешаются только после фактического wait. Отдельный сценарий оставляет настоящий зависший worker живым, моделируя отказ native adapter; новая правка выполняет повтор остановки и лишь после успеха запускает замену. При отказе destroy handle также сохраняется до явной успешной повторной попытки. Все вызовы C# binding к session handle привязаны к WPF-потоку; конкурентное уничтожение не заявляется поддержанным.

В сценарии гибели owner наблюдатель завершает только отдельный процесс владельца, не дерево. Worker заранее находится в spin-loop, не читает EOF и не имеет активного запроса с таймером у контроллера; его выход подтверждён по заранее открытому process handle. В основном сеансе после cleanup — ноль worker, ноль неосвобождённых ABI-буферов и отсутствие callback после возврата destroy. Отдельная проверка ОС не обнаружила оставшихся процессов стенда. Окончание IO-потока, ошибка чтения и настоящий EOF отмечены раздельно, без вывода о полном дочитывании только из join.

В шести обычных примерах путь от WPF-обработчика до применения ответа занял **0,2143–5,6770 мс**, ABI-вход — **0,0140–0,2340 мс**. Это выбранный корпус после готовности worker, не p95 всего продукта и не физическая клавиатура/отрисовка монитора. При пороге 200 мс состояние timeout применялось на **207,9857–214,9435 мс**, выход процесса подтверждался на **209,8574–216,7980 мс**. Полный бюджет ровно 200 мс **не подтверждён**; принятый предел не увеличен. Допуск ответа по монотонному сроку и фактическая реакция ОС остаются разными измерениями.
