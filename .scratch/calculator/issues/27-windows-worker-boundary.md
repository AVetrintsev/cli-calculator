## Question

Проверить техническую предпосылку выбора отдельного вычислительного процесса: на доступной Windows реально создать дочерний процесс уже внутри Job, завершить его при некооперативном численном вызове и заполненном pipe, отвергнуть запоздавший ответ, пережить внутренний выход worker без автоматического повтора и убрать worker при смерти владельца Job. Отдельно измерить срок допуска ответа и фактический выход. Это ограниченный AFK-стенд для решения [Общее ядро и платформенные оболочки](09-shared-core-and-shells.md), не реализация продукта.

## Context

Использовать имеющийся .NET 9 и Win32, без установки toolchain и новых зависимостей. Это проверка нативной границы, не производительности Rust/Dashu, не полного 200-мс пути калькулятора и не macOS. Все процессы и временные файлы принадлежат стенду; пользовательский нативный прототип, системный фокус, буфер и данные не затрагиваются. Поведение при аварии принято в пункте 41.1 архитектурного вопроса; закрытия всей архитектуры стенд не ждёт. Первичный код и наблюдения сохраняются на отдельной ветке, основной проект — только вывод и ссылку.

## Answer

Технический стенд выполнен: 11/11 сценариев механизма, Release-сборка без ошибок/предупреждений, .NET SDK 9.0.317 и runtime 9.0.20, x64, Windows build 26200. Проверены назначение Job при создании, обычный ответ, прекращение настоящего некооперативного BigInteger.Pow, stdout при отложенном чтении с контрольным drain, независимость watchdog от непрочитанного stdin, допуск актуального ответа, восстановление без автоматической отправки упавшего запроса, оборванный/слишком большой кадр, EOF и гибель владельца Job. После опыта процессов стенда не осталось.

В parent-death worker находится в бесконечном Sleep и не читает stdin; observer держит только process handle и завершает только owner. Его выход поэтому не объясняется обычным EOF или обходом дерева процессов. Перед отрицательными утверждениями о результатах после kill ожидается завершение reader до EOF: сигнал process handle сам по себе не означает, что очередь сообщений уже опустошена. Контроль stdout дополнен длительностью Write+Flush на стороне worker; точный профиль наполнения kernel-buffer не измерялся.

Граница фактической остановки **200 мс не подтверждена**. В последнем прогоне вызов TerminateJobObject происходил на 202,8016–208,2475 мс, сигнал process handle — на 208,4330–216,5342 мс. Эти данные доказывают необходимость отдельного допуска ответа по сроку и актуальности; изменять принятый бюджет или объявлять его пройденным нельзя. Проверка отрицательного допуска 200,01 мс — введённое значение fixture, не полный измеренный путь UI/парсинга/IPC.
