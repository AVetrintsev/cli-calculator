# Проверка точности десятичного численного слоя

## Question

Собрать ограниченный одноразовый Rust-стенд с опубликованным Dashu 0.6.0 и проверить пригодность его численного слоя для согласованных 30 значащих десятичных цифр: точные половины от нуля, цепочки округления, границы целого/малого ненулевого значения и представительные сложные функции. Сопоставить результаты с независимыми точными или интервальными эталонами. Отделить округление отдельного вызова от всей композиции функции и от форматирования. Эксперимент должен выявить реальные несовместимости для [Общее ядро и платформенные оболочки](09-shared-core-and-shells.md), а не реализовать весь язык калькулятора.

## Context

Среда при необходимости готовится изолированно в папке эксперимента без изменения глобального PATH или системных настроек. Уже доступный Windows .NET-стенд не является проверкой Rust/Dashu. Численный код, зафиксированные зависимости, эталоны и наблюдения хранятся в отдельной ветке; основной проект получает только вывод и ссылку. Это не приёмка всего приложения, не перенос результата на macOS и не автоматическое утверждение стека. Правила чисел берутся из [numbers.json](../language/numbers.json); подтверждать их заново у пользователя не нужно.

## Answer

Ограниченный эксперимент выполнен: **192/192** конечных результатов совпали с независимым эталоном — 175 числовых ответов и 17 ожидаемых диагностик. Release-сборка Rust 1.98.1 / Dashu 0.6.0 прошла без ошибок и предупреждений на Windows 11 x64, build 26200. Официальные компоненты Rust, linker из rust-mingw и эталон gmpy2 2.3.1 / MPFR 4.2.2 подготовлены внутри папки эксперимента с проверкой SHA256, без системной установки. Зависимости закреплены в Cargo.lock, запуск воспроизводится скриптами стенда.

Точные рациональные эталоны Python Fraction проверяют базовую арифметику, цепочки рабочего округления, целые степени и выбранные финансовые формулы. Направленные MPFR-границы с точностью 384 бита независимо определяют округлённые трансцендентные ответы. Сравнение использует статус и точные коэффициент/экспоненту; короткий экранный формат не участвует. Проверены положительные/отрицательные половины и их соседи, перенос разряда, целое переполнение, вход ниже минимума, проверка результата после рабочего округления, малые ненулевые значения, выбранные корни/логарифмы/тригонометрия/степени и 96 случаев с фиксированным seed.

**Одного Context с точностью 30 недостаточно.** У прямых библиотечных вызовов найдено 22 числовых расхождения с контрактом: 11 add, 9 sub, 2 div вернули 31 значащую цифру. Собственный слой точной арифметики над IBig с явным округлением до 30 устраняет эти расхождения. Это подтверждает необходимость отдельного десятичного адаптера, а не передачу ответственности за рабочее значение одной настройке библиотеки. Например, в `seeded-div-2` прямой коэффициент `1843302439289243078286406408119` при экспоненте −26 отличается от правильного `184330243928924307828640640812` при −25.

Для синуса в градусах выполнены точная редукция угла и направленная композиция; для выбранных накопления и аннуитета — ограничение общей ошибки атомарной формулы. 12 случаев завершились на 40 внутренних цифрах, два аннуитета с очень малыми ставками — на 80. Это не доказательство достаточности фиксированного запаса для всего каталога. Отрицательные ставки аннуитета и остальные финансовые модели стендом не покрыты. Финансовая встроенная функция с конечным округлением не приравнивается к текстовой формуле, округляющей каждую промежуточную операцию.

В первом прогоне ошибка отрицания границ внутри самого MPFR-эталона дала одно расхождение на большом угле. Явный направленный контекст и проверка точности границ исправили эталон без изменения Rust-алгоритма. Итоговый отчёт содержит успешный прогон. Независимый аудит не нашёл ложноположительных конечных сравнений; сами Dashu lo/hi не экспортируются и их включение точного значения отдельно не проверено. Нижняя граница вычисленного значения проверяется после 30-значного округления, как уже принято в numbers.json; близкий результат ниже 10^(-1000) может округлиться к включительной границе.

Первичный материал: ветка `codex/prototype-decimal-core`, коммит `30c30f472746b1b16750be46ea053d92a8c21460`. [Код, запуск, методика и границы](C:/Users/vetrintsev/.codex/visualizations/2026/09/10/01a08a29-3083-7091-8d85-c955198837d6/decimal-core/.scratch/calculator/prototypes/decimal-core/README.md); [машиночитаемые наблюдения](C:/Users/vetrintsev/.codex/visualizations/2026/09/10/01a08a29-3083-7091-8d85-c955198837d6/decimal-core/.scratch/calculator/prototypes/decimal-core/observations/numeric.json). Основной проект хранит выводы и указатель, код остаётся на отдельной ветке.

Результат поддерживает кандидата IBig + собственное округление + отдельные алгоритмы Dashu, но не закрывает [Общее ядро и платформенные оболочки](09-shared-core-and-shells.md). Полный язык/lazy, все сложные функции и их области, форматирование, C ABI, Rust-контроллер/worker, редактор, хранилище и macOS здесь не проверялись. Внутреннее время операции исключает разбор, IPC, UI и запуск процесса; пятисекундный предохранитель стенда не является принятым бюджетом 200 мс. Продуктовых правил, пользовательских настроек и надписей этот эксперимент не меняет.
